Buncha, my first project

Shopper auto assignment

How I turned a dispatcher's daily judgement call into something a system can make.

01The gap I noticed

Shadowing dispatch for two weeks, I saw that the problem wasn't slow dispatchers. Every run, they re-made the same judgement call from memory: who's fast, who's free, who gets what. Two people rarely made it the same way.

02How I reframed it

Treat it as a workforce-data problem, not a people problem. If the system knows who is really on shift and how fast each shopper actually picks, the judgement can be computed.

illustrative

03Decisions that shaped it

  1. Fair, not just fastEach shopper is filled to 85–110% of a target based on their share of the team's speed, so the fastest people aren't quietly overloaded.
  2. Right order, right shopperBig orders go to faster tiers, and VIP and first-time customers go to stronger shoppers.
  3. Make the bypass a featureSix named reasons a dispatcher can take over, including 2-hour windows the design deliberately doesn't cover.
  4. Trust only real availabilityShifts come from When I Work, and a sync failure is surfaced, never silently worked around.

04How I got there

  1. 10–15 days shadowing dispatch
  2. PRD
  3. Logic design
  4. Rollout, owned solo

05Where it landed

94.5%of runs now assign themselves
1.59%go to a dispatcher

Buncha, owned 0 to 1

Capacity automation

How I replaced a per-run guess with a number grounded in who's actually on shift.

01The gap I noticed

Run capacity was a number a dispatcher estimated for every run, disconnected from the actual shift schedule. Two dispatchers, same store, different numbers.

02How I reframed it

The fix wasn't a stricter process for dispatchers. It was tying capacity to real workforce data, so the number reflects who is actually on the floor.

illustrative

03Decisions that shaped it

  1. An honest zero beats a confident guessNo eligible shift means zero capacity, not an estimate that looks fine and fails later.
  2. Protect the new shoppersTenure-based floors, so a newcomer's thin history doesn't drag down a whole store's capacity.
  3. Design the override, don't tolerate itEvery manual edit needs a reason. That turned the escape hatch into the best signal of where the formula was blind.
  4. Prove the pattern, then extend itShift-matching proved itself on capacity first, which made driver assignment a small step instead of a new bet.

04How I got there

  1. Audit the manual process
  2. Formula design
  3. Phase 1, then 1.5, then 2

05Where it landed

90%of 2,500 runs calculated automatically
Staffingnot logic, explained the gaps

Buncha, product strategy

One van, multiple stores

How one question, why does a van belong to one store, changed the cost of delivery.

01The gap I noticed

Some refrigerated vans left with just one or two orders: full dispatch cost for a fraction of the capacity, because each van was tied to a single store.

02How I reframed it

Instead of asking how to fill a store's van, I asked why a van belongs to one store at all. One van can serve several stores in a row whenever timing and distance allow.

03Decisions that shaped it

  1. Real travel time, without the billFeasibility is checked for every possible pairing, so I chose self-hosted routing (Valhalla) over per-call Google Maps pricing.
  2. Count the trip homeA late return delays the next run, so getting back to the store on time is part of the feasibility check.
  3. Don't stretch the route for outliersFar-off orders go to independent drivers instead of dragging the van off course.
  4. Decide once orders settleClustering runs 90 minutes before the run, when the order set is stable.
Clustered orders, W2 vanOutliers, 1099 driver

04How I got there

  1. Frame cost as a product problem
  2. Build-vs-buy call on routing
  3. Worked example: Meijer 52 + Store 208

05Where it landed

15–25%fewer vans (directional)
$4.95flat delivery promise kept

Good Business Lab, worker safety

Inache grievance redressal

How one comment in a user interview exposed a safety gap in a product built to protect workers.

01The gap I noticed

In a user interview, a complaint surfaced that callers could be recognised by their voice. The line promised migrant workers anonymity, but the saved recording quietly broke that promise.

02How I reframed it

This wasn't one bug to patch. Every layer that touches a case, from the audio to transcripts, location tags and even risk scores, is a possible leak. Safety had to cover the whole system.

illustrative

03Decisions that shaped it

  1. Disguise the voice before anyone hears itMorph the audio on save, and lock the original away with an access log.
  2. From reacting to warning earlyFlag risky locations and reps from patterns, using only de-identified data.
  3. A signal, not a verdictFlags go to a human reviewer first, because a wrongly flagged rep is harmed too.
  4. Sensitive cases get special handlingHarassment and coercion cases go only to trained reps, always with senior visibility.

04How I got there

  1. Heard it in user interviews
  2. Flagged it to my manager
  3. Explored directions with the team
  4. Wrote the PRD as my proposal

05Where it landed

Builtthe team shipped an anonymisation fix after I left

Side project, live

Last Sip

How I designed around the data no grocery app will share.

01The gap I noticed

Grocery apps remember what you bought and let you reorder, but none tell you you're about to run out. And none can see what you buy on the other apps you use.

02How I reframed it

Predict from how fast you use things, not from what you bought before, and work across every app instead of inside one.

illustrative

03Decisions that shaped it

  1. Design around the missing dataNo grocery app shares your orders, so a one-tap “I've ordered” teaches Last Sip your real pace.
  2. Batch, don't nagThe real pain is the convenience fee on small orders, so nudges group items into one basket email.
  3. No subscriptionsFixed delivery dates ignore how fast you actually use things.
  4. A friend, not a sales pushPlayful messages, one digest a day, never at night.

04How I got there

  1. Checked what apps already do
  2. Wrote the PRD
  3. Prototyped the flow
  4. Built and shipped it solo

05Where it landed

Side project, live

Visa Didi

How I'd build an AI assistant people can trust with a high-stakes answer.

01The gap I noticed

Indian travellers get visa answers from blogs, agents and AI chatbots, and a wrong one can cost a trip. When I checked, travel sites quoted different UK visa fees, and Thailand's rules for Indians had changed twice in 2026.

02How I reframed it

Don't try to know everything. Answer only from official pages, show when each one was last checked, and say "I don't know" when they don't cover the question.

illustrative

03Decisions that shaped it

  1. Official sources onlyBlogs, agents and forums never enter what Visa Didi knows, even when they rank first on Google.
  2. Dated, not just citedEvery answer shows its source and the day it was last checked, because visa rules change without notice.
  3. Refusing is a featureNo approval predictions, no agent picks, and no guessing beyond the sources. A confident wrong answer is the worst outcome.
  4. Measure it against the alternativeA 40-question test set scores Visa Didi against Claude and ChatGPT, with 13 questions on rules that changed in 2026.

04How I got there

  1. Mapped official sources for 12 destinations
  2. Wrote the PRD
  3. Built a 40-question test set
  4. Built and shipped it solo

05Where it landed

Liveon Vercel, built solo with AI tools
12destinations, from Thailand to the US
40test questions to benchmark it against Claude and ChatGPT
